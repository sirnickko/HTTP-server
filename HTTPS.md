# Project 2 — HTTPS

> What you'll learn: certificates, chain of trust, symmetric vs asymmetric
> encryption, why HTTPS matters.

---

## Architecture

```
Port 8080 (HTTP)  ──→  301 Moved Permanently ──→  https://host:4433/...
Port 4433 (HTTPS) ──→  rustls TLS handshake  ──→  serve request
                        └─ HSTS header on every response
```

In production swap the ports: `80` for HTTP redirect, `443` for HTTPS.

---

## Route 1 — TLS via Rust's standard library (rustls)

The server uses **rustls** (a pure-Rust TLS 1.2/1.3 implementation) to wrap
every accepted `TcpStream` in a TLS session before passing it to the HTTP
handler.  No OpenSSL, no C code (except `ring`'s assembly crypto primitives).

### Development: self-signed certificate (generated in-memory)

```bash
cargo run
```

`rcgen` generates a fresh RSA-2048 self-signed certificate for `localhost` /
`127.0.0.1` each time the server starts.  The private key never touches disk.

Test it (expect a certificate warning — that's expected for self-signed):

```bash
# Skip verification:
curl -k https://localhost:4433/

# Or supply the cert manually:
openssl s_client -connect 127.0.0.1:4433 -CAfile cert.pem
```

## Route 2 — External PEM certificate (OpenSSL / Let's Encrypt)

### Step 1 — Generate a self-signed cert with OpenSSL

```bash
openssl req -x509 -newkey rsa:4096 \
  -keyout key.pem -out cert.pem \
  -days 365 -nodes \
  -subj "/CN=localhost" \
  -addext "subjectAltName=DNS:localhost,IP:127.0.0.1"
```

### Step 2 — Run the server with PEM files

```bash
cargo run -- --cert cert.pem --key key.pem
```

### Step 3 — Let's Encrypt on a real domain

1. Point a DNS A-record at your server's public IP.
2. Install `certbot`:
   ```bash
   sudo apt install certbot          # Debian/Ubuntu
   ```
3. Obtain a certificate (standalone mode — temporarily uses port 80):
   ```bash
   sudo certbot certonly --standalone -d yourdomain.com
   ```
4. Certificates land in `/etc/letsencrypt/live/yourdomain.com/`.
5. Run the server:
   ```bash
   sudo cargo run -- \
     --cert /etc/letsencrypt/live/yourdomain.com/fullchain.pem \
     --key  /etc/letsencrypt/live/yourdomain.com/privkey.pem \
     --https-port 443 \
     --port 80
   ```

## Inspecting the handshake

### openssl s_client

```bash
# See the full certificate chain and TLS negotiation:
openssl s_client -connect 127.0.0.1:4433

# With a CA file (for self-signed certs generated by OpenSSL):
openssl s_client -connect 127.0.0.1:4433 -CAfile cert.pem

# Show certificate details:
openssl s_client -connect 127.0.0.1:4433 </dev/null | openssl x509 -text -noout
```

You'll see output like:
```
subject=CN=localhost
issuer=CN=localhost             ← self-signed: issuer == subject
TLSv1.3, Cipher is TLS_AES_256_GCM_SHA384
```

### Wireshark

1. Capture on `Loopback` interface, filter: `tcp.port == 4433`
2. You'll see:
   - **ClientHello** — browser's supported cipher suites, TLS version, random nonce
   - **ServerHello** — server picks cipher suite, sends its nonce
   - **Certificate** — server's X.509 cert (public key inside)
   - **CertificateVerify** — server signs a transcript hash with its private key
   - **Finished** — both sides confirm the handshake with a MAC
   - From here on: **ApplicationData** (opaque encrypted records)

## What the code does

### `src/tls.rs`
- `build_self_signed()` — generates an in-memory RSA self-signed cert with `rcgen`
- `build_from_files(cert, key)` — loads PEM chain + key from disk for production
- `accept(config, tcp)` — performs the TLS handshake, returns a `TlsStream`

### `src/server.rs`
- `handle_http_redirect(stream, https_port)` — reads the `Host` header, responds
  with `301 Moved Permanently` to `https://`
- `handle_connection<S: Read + Write>(stream)` — generic over any stream type
  (plain TCP *or* TLS-wrapped); injects **HSTS** on every response

### `src/main.rs`
- Binds **two** `TcpListener`s: one for HTTPS (port 4433/443), one for HTTP (8080/80)
- HTTP thread: redirect loop
- HTTPS main loop: wraps each accepted `TcpStream` with `tls::accept()` before
  handing off to `server::handle_connection`

### `src/request.rs`
- `parse()` now takes `BufReader<impl Read>` instead of `BufReader<&TcpStream>` —
  the same parser works for both plain and TLS streams

## Why HTTPS matters (the theory)

| Concept | What it means here |
|---------|-------------------|
| **Asymmetric encryption** | Server's RSA/ECDSA key pair: public key in the cert (anyone can see), private key never leaves the server. Used during the handshake to authenticate and establish a shared secret. |
| **Symmetric encryption** | After the handshake, both sides use a shared AES-256-GCM key derived from the handshake. Fast, used for all actual data. |
| **Chain of trust** | A CA (e.g. Let's Encrypt) signs your cert with its private key. Browsers trust Let's Encrypt's root, so they trust your cert. Self-signed certs have no such chain — browsers warn because they can't verify who you are. |
| **HSTS** | Once a browser receives this header it will *never* send a plain HTTP request to your domain again (for `max-age` seconds), even if the user types `http://`. Prevents SSL stripping attacks. |
